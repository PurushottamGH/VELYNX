# v0.1.0 Release Gate

Status: Of the four blockers identified across independent audit rounds,
all four have engineering-side resolutions recorded below (Section 4).
Three of those resolutions (Blockers 1, 2, 4) are complete as staged,
locally- and fresh-environment-verified work, ready for human review and
commit. Blocker 3 (an immutable, CI-verified release candidate) cannot be
closed by engineering work alone — it requires a human commit, a green
CI run, and a tag. Section 8 records the exact evidence fields that only
come into existence after that human action; every field there reads
**PENDING HUMAN RELEASE** until it does. This document does not itself
constitute release approval.

## 4. Release blockers reconciled

### Blocker 1 — Distribution version conflicted with release target

- Root cause: `p1/tooling/pyproject.toml` declared `version = "1.0.0"`,
  conflating the frozen Research OS Specification/schema version `1.0` with
  the Project P1 software release version `0.1.0`.
- Fix: changed `[project].version` in `p1/tooling/pyproject.toml` from
  `1.0.0` to `0.1.0`. Updated `tests/p1_os/test_installation.py`:
  `test_p1_os_is_an_installed_distribution` now asserts installed version
  `0.1.0`; `test_pyproject_declares_p1_os_package` now additionally asserts
  `data["project"]["version"] == "0.1.0"`.
- Explicitly not changed: `schema_version: "1.0"` in any schema, template,
  or fixture; the frozen specification; `p1/tooling/p1_os/__init__.py`; the
  historical Milestone 1.1 acceptance report (which accurately records the
  earlier `1.0.0` build and is left as historical evidence).

### Blocker 2 — No functioning P1 CI release gate

- Root cause: `.github/workflows/ci.yml` is a legacy VELYNX workflow. It
  installs the root package via `pip install -e .`, never runs
  `tests/p1_os`, and suppresses some failures with `|| true`. It provides no
  clean-checkout release gate for the `p1-os` distribution.
- Fix: created `.github/workflows/p1-release.yml`, a new, isolated workflow
  named **P1 Release Gate** (Python 3.11, `ubuntu-latest`) that:
  - installs `p1/requirements-dev.txt`, editable `p1/tooling`, and
    `build==1.5.0`;
  - collects then runs the full `tests/p1_os` suite with no
    `continue-on-error` or `|| true`;
  - builds wheel and sdist into `dist/p1` via
    `python -m build --outdir dist/p1 p1/tooling`;
  - asserts the `0.1.0` wheel and sdist filenames exist;
  - installs the built wheel into a separate temporary virtual environment
    and imports `p1_os`, `p1_os.frontmatter`, and `p1_os.schemas` from a
    temporary directory outside the repository, asserting
    `importlib.metadata.version("p1-os") == "0.1.0"`;
  - records `pip freeze`, pytest output, build output, the source commit
    SHA, and a `SHA256SUMS` file as evidence;
  - uploads the built distribution and evidence via
    `actions/upload-artifact@v4`.
  - The legacy `.github/workflows/ci.yml` was not modified.

### Blocker 3 — No immutable, reviewable release candidate

- Root cause: at the start of this work, all active `p1/`, `tests/p1_os/`,
  and `tests/fixtures/p1_os/` files were untracked in Git, and
  `.gitignore`, `REPOSITORY_CONSTITUTION.md`, and `RESEARCH_PROTOCOL.md` had
  uncommitted modifications. No commit existed against which CI, hashes, or
  reviewer approval could anchor.
- Fix (this work): local and fresh-environment verification (Section 5) was
  completed and this record was written. Staging of the exact authorized
  paths, human commit/push, a green **P1 Release Gate** run on that commit,
  and tag creation remain outstanding human release actions — see Section 7.
- Explicitly excluded from staging: the eight pre-existing untracked
  `theory/*` files, `p1/tooling/p1_os.egg-info/`, `__pycache__/`,
  `.pytest_cache/`, any temporary build directory, `.env`, and
  `gcp-key.json.json`.
- This blocker cannot be fully closed by engineering work alone: an
  immutable candidate requires a human commit. Its status after this work
  is **PENDING HUMAN RELEASE** (commit, push, green CI, tag — Section 7),
  not resolved.

### Blocker 4 — Reconciling "no architecture/methodology changes" with the staged governance-boundary documentation

- Root cause (audit finding): the independent audit correctly observed
  that this candidate modifies `REPOSITORY_CONSTITUTION.md` (adds a `p1/`
  directory entry, lines ~52-54) and `RESEARCH_PROTOCOL.md` (adds a scope
  note, line ~5), and adds `p1/methodology/STATUS_LIFECYCLE.md`. An earlier
  version of this record's framing did not distinguish these from the
  prohibited category "architecture, ontology, or methodology changes,"
  which caused a legitimate gate failure.
- Reconciliation: two distinct categories were being conflated under one
  label. This candidate contains changes from only the first category:
  - **Approved release-governance boundary documentation (in scope for
    this work):** the `REPOSITORY_CONSTITUTION.md` addition states that
    `p1/` is governed by the approved P1 Research OS specification and PI
    decisions rather than by VELYNX directory-placement/SQLite rules, and
    that P1 tooling must not depend on VELYNX `backend/`/`frontend/`. The
    `RESEARCH_PROTOCOL.md` addition states that protocol governs VELYNX
    Program D experiments, and that P1 Research OS records/experiments are
    governed separately. `p1/methodology/STATUS_LIFECYCLE.md` is
    explicitly descriptive-only (see its own Scope line and Milestone 1.1
    acceptance review) — it records what the frozen Milestone 1 schemas
    already allow and what the frozen specification already authorizes;
    it adds no enforcement code and defines no new state, transition, or
    scientific claim. None of these three files add, remove, or alter a
    VELYNX hypothesis, the Knowledge Ontology, the Research Process, the
    Research OS Specification, a frozen constant, or any scientific
    methodology rule.
  - **Prohibited scientific/architectural redesign (out of scope, and not
    present in this candidate):** changes to `theory/HYPOTHESIS_REGISTER.md`
    or other protected-canon hypothesis files, the Knowledge Ontology, the
    Research OS Specification, frozen constants, VELYNX `backend/`/
    `frontend/` runtime architecture, or the scientific method defined in
    `RESEARCH_PROTOCOL.md` Sections 1+. No file in this category is staged.
- Verification: `git diff --cached -- REPOSITORY_CONSTITUTION.md
  RESEARCH_PROTOCOL.md` shows only the two boundary-scoping additions
  quoted above; no existing section was deleted or rewritten. No file
  under `theory/` is staged (the eight `theory/*` files present in the
  worktree are untracked and excluded — Blocker 3).
- Corrected gate criterion going forward: the release gate's
  architecture/methodology check should read as "no VELYNX ontology,
  hypothesis-register, Research OS Specification, frozen-constant, or
  scientific-methodology changes," not "no diff touches any file with
  'architecture' or 'methodology' in its path." Under the corrected
  criterion this blocker is **resolved**; under the original, overly broad
  wording it would incorrectly fail on any release-governance
  documentation, including boundary notes required to make `p1/` a legible
  release surface at all.

## 5. Verification performed

### Local (existing `.venv`)

```
.venv/Scripts/python.exe -m pip install --no-deps -e p1/tooling
.venv/Scripts/python.exe -m pytest tests/p1_os --collect-only -q
.venv/Scripts/python.exe -m pytest tests/p1_os -q
.venv/Scripts/python.exe -c "from importlib.metadata import version; assert version('p1-os') == '0.1.0'"
```

Result: 382 tests collected, 382 passed, installed version `0.1.0`.

<tmp-venv>/Scripts/python.exe -m pip install -r p1/requirements-dev.txt
<tmp-venv>/Scripts/python.exe -m pip install --no-deps -e p1/tooling
<tmp-venv>/Scripts/python.exe -m pytest tests/p1_os -q
```

Result: `p1-os==0.1.0` installed; 382 passed. Temporary environment deleted
after verification.

### Build and packaging

```
.venv/Scripts/python.exe -m build --outdir <tmp-dist-dir> p1/tooling

Result: `p1_os-0.1.0-py3-none-any.whl` and `p1_os-0.1.0.tar.gz` produced.
